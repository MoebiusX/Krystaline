# Anatomy of a Trade

> The canonical span-by-span breakdown of one market BUY on the full RabbitMQ path — the single source of truth for the "17+ spans" claim.

A market BUY produces **typically 17+ spans across 4 services (observed in demo traces)**: `kx-wallet` (browser), `api-gateway` (Kong), `kx-exchange` (Express API), and `kx-matcher` (order matcher). That number is not marketing — it is derived below from the instrumentation source, span by span. Every hand-written span name in this document is quoted from code with a file link; where spans are generated by auto-instrumentation, the naming pattern is given instead of an invented literal name. Everything here is [PUBLIC] — in-repo source you can read and run.

Actual counts vary per trace: fills and retries add spans, Express middleware and PostgreSQL query spans depend on the exact request, the gateway segment only appears when the request is routed through Kong, and the collector applies tail-based sampling — though a policy in [`config/otel-collector-config.yaml`](../config/otel-collector-config.yaml) (lines 35–55) keeps **every** trace touching `kx-matcher`/`payment-processor`, so trade traces are never sampled away.

The arithmetic behind "17+": **10 hand-written spans** (2 in the browser, 1 broker publish, 2 in the matcher, 5 `zk.*`) plus **7 or more auto-instrumented spans** (browser fetch, Express HTTP server + middleware, PostgreSQL queries, amqplib publish/consume) on a successful FILLED BUY.

## The Span Table

Span kinds: `INTERNAL` (default), `CLIENT`, `SERVER`, `PRODUCER`, `CONSUMER`. "Manual" means the span name is a string literal in our code; "auto" means an OpenTelemetry instrumentation library generates it.

### Segment 1 — Browser (`kx-wallet`)

The browser is a first-class traced service: [`client/src/lib/otel.ts`](../client/src/lib/otel.ts) registers a `WebTracerProvider` with `service.name: 'kx-wallet'` (line 31) exporting OTLP/HTTP to the collector's browser-facing port 4319.

| # | Service | Span name (as coded) | Kind | What it proves |
|---|---------|----------------------|------|----------------|
| 1 | kx-wallet | `order.submit.client` | INTERNAL | The trace starts in the user's browser, before any network call. Manual span with `order.side` / `order.quantity` / `order.pair` attributes — [`client/src/components/trade-form.tsx:155`](../client/src/components/trade-form.tsx) |
| 2 | kx-wallet | auto: `@opentelemetry/instrumentation-fetch` names its spans `HTTP <METHOD>` | CLIENT | The `fetch()` POST carried a W3C `traceparent` header out of the browser (propagation config at [`client/src/lib/otel.ts:79-85`](../client/src/lib/otel.ts)) |
| 3 | kx-wallet | `order.response.received` | INTERNAL | The browser saw the execution result (`order.status`, `order.fillPrice` attributes) inside the same client span tree — [`client/src/components/trade-form.tsx:193`](../client/src/components/trade-form.tsx) |

### Segment 2 — Gateway (`api-gateway`)

Kong's OpenTelemetry plugin is enabled at startup by [`scripts/enable-kong-otel.js`](../scripts/enable-kong-otel.js), which sets `service.name: 'api-gateway'` and `header_type: 'w3c'` (lines 27–36). Kong's spans are entirely auto-generated: with `KONG_TRACING_INSTRUMENTATIONS=all` Kong emits a proxy request span plus per-phase child spans following Kong's own `kong.*` naming (exact names depend on the Kong version — we do not hand-write any of them).

| # | Service | Span name (as coded) | Kind | What it proves |
|---|---------|----------------------|------|----------------|
| 4 | api-gateway | auto: Kong OTel plugin, `kong`/`kong.*` phase naming | SERVER + children | The request transited the gateway and Kong preserved the browser's trace context (`header_type: 'w3c'`) rather than starting a new trace |

*Honesty note:* this segment appears when the request is routed through Kong on `:8000` — the e2e suite and load scripts do this, and the browser does when `VITE_KONG_URL` is set. With the default dev Vite proxy the browser calls `:5000` directly and the gateway segment is absent, which is one reason counts vary.

What makes it interesting is *where it lands*: [`server/core/order-service.ts:270`](../server/core/order-service.ts) restores the captured POST context with `context.with()` after the RabbitMQ round-trip, so these spans join the original HTTP trace instead of dangling.

### Segment 7 — Proof (`kx-exchange`, `zk.*` family)

On FILLED, [`server/core/order-service.ts:287-294`](../server/core/order-service.ts) fires `zkProofService.generateTradeProof()` — non-blocking, `.catch`-guarded, so a failed proof never affects the trade. Because it is launched inside the restored POST context, the entire proving pipeline records into the **same trace** — and the trace ID itself is a private input to the circuit, so the proof is cryptographically bound to the trace you are looking at.

## How the Async Hop Stays in One Trace

The hard part of this trace is not the HTTP hops — W3C propagation handles those. It is the RabbitMQ round-trip: the API publishes an order, a separate process consumes it, replies on another queue, and the API's awaited Promise continues *after* the reply arrives, in whatever context the consumer callback happens to have. Naive instrumentation loses the trace right there.

Krystaline uses a **dual-context pattern** — two trace contexts travel on every order message:

1. **`traceparent`** — the `publish orders` span's context, injected at [`server/services/rabbitmq-client.ts:183-185`](../server/services/rabbitmq-client.ts). The matcher extracts it and parents `order.match` under it ([`payment-processor/index.ts:171,179`](../payment-processor/index.ts)). This gives the correct producer → consumer hierarchy.
2. **`x-parent-traceparent`** (+ `x-parent-tracestate`) — the *original POST span's* context, injected alongside at [`server/services/rabbitmq-client.ts:188-209`](../server/services/rabbitmq-client.ts). The matcher does not parent anything under it; it stashes it ([`payment-processor/index.ts:174-176,193`](../payment-processor/index.ts)) and **echoes it back as the reply message's `traceparent`** ([`payment-processor/index.ts:261-268`](../payment-processor/index.ts)).

When the reply lands, the API's response consumer extracts that echoed context and invokes the pending callback *inside* it via `context.with()` ([`server/services/rabbitmq-client.ts:289-313`](../server/services/rabbitmq-client.ts)) — so the awaited `submitOrder` continuation resumes with the POST span as its ambient parent. As a belt-and-braces measure, `submitOrder` also captures its own context before the round-trip and re-pins it with `context.with(currentContext, ...)` before settlement ([`server/core/order-service.ts:225,270`](../server/core/order-service.ts)). The result: wallet settlement queries and all five `zk.*` spans join the trace that began with a button click in the browser.

The full pattern, including the failure modes it avoids, is documented in the [OTel Tracing Guide](observability/01_OTEL_TRACING_GUIDE.md) (§5 consumer context extraction, §8 Express async handler context loss — both referenced from the code comments themselves).

## Verify It Yourself

None of the above asks for trust — the whole path runs on your machine in about five minutes:

1. Follow the [5-Minute Quick Start](GETTING_STARTED.md): `git clone`, `npm install --legacy-peer-deps`, `npm run dev` (Docker Desktop must be running; the script composes the infrastructure itself).
2. Register at http://localhost:5173 (verify the email via MailDev at http://localhost:1080) and buy 0.001 BTC.
3. The success toast contains a **"View Full Trace in Jaeger"** deep link built from the real trace ID ([`client/src/components/trade-form.tsx:268`](../client/src/components/trade-form.tsx)) — or open [Jaeger](http://localhost:16686) directly and find the trace. Count the spans against the table above.
4. Verify the trade's Groth16 proof at `GET http://localhost:5000/api/public/zk/verify/:tradeId` — the server runs a real `snarkjs.groth16.verify()` and returns the mathematical verdict.

For the machine-checked version of the same claim: the e2e suite ([`scripts/e2e-test.js`](../scripts/e2e-test.js)) **mints a random 128-bit trace ID client-side** (lines 320–325), sends it as the `traceparent` header through Kong (line 351), then queries Jaeger for that exact ID and asserts the trace exists with **at least 3 spans across multiple services**, retrying with backoff for up to 25 seconds (lines 365–395). If context propagation broke anywhere on the path above, that assertion fails. The suite runs via a manually-triggered `workflow_dispatch` CI job ([`.github/workflows/e2e-tests.yml`](../.github/workflows/e2e-tests.yml)) — it needs the full stack, so it is not a per-PR check.

To see what this trace looks like when things go *wrong*, run a scenario from the [Chaos Injection System](CHAOS_INJECTION.md) — injected latency shows up in these exact spans, and the anomaly detector flags them against learned baselines.
